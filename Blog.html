MHA: That Scalar Weight Thing and Why V Might Be Underrated

Quick MHA Recap (You Probably Know This)

Alright, What's Multi-Head Attention? Look, I'm assuming if you're here, you've got some idea about basic attention and maybe even MHA already. If not, this probably isn't the best starting point (and don't ask me if I know it perfectly, I just think I do).

But quick recap anyway: You take your input sequence (with embedding dimension, let's say d_model), transform it using learned linear layers into Query (Q), Key (K), and Value (V) tensors, all typically still d_model size. Mash the Query and Key together (usually a scaled dot product: softmax(Q @ K^T / sqrt(d_k))) to see how relevant they are that gives you attention scores (one score per query-key pair). Use those scores to create a weighted average of the Value tensors, and finally, run that result through one last output linear layer. We get, attention.

So, the "Multi-Head" bit? The idea is that maybe one big attention calculation tries to average too many things. MHA lets you do this in parallel. Instead of one big calculation, you have, say, h heads doing smaller calculations simultaneously. Each might specialise in a few things (Read about Induction Head, etc.). The common implementation is: after getting your main Q, K, V (all d_model deep), you use linear projections and then reshape/split their embedding dimension (d_model) into h chunks. Each chunk now has a smaller dimension, d_k = d_model / h. So, head 1 gets the first d_k dimensions of the transformed Q, K, V, head 2 gets the next d_k, and so on. Each head then runs the attention calculation (that scaled dot product thing) separately using only its own little d_k-dimensional chunk of Q, K, and V. Afterwards, you stitch the d_k-dimensional results from all h heads back together (concatenating them) and usually run it through that final output projection layer (W_O). Parallel processing, different perspectives, good shit.

The Scalar Weight Thing... Kinda Basic When You Think About It?

Okay, revision over. Here's something I didn't really clock until I started thinking about it more: Standard attention, even with multiple heads, calculates one single scalar attention weight (that a_ij thing) for each query i and key j pair. This number pops out after comparing their whole vectors (either the full d_model one or the smaller d_k chunk in a head).

And here’s the part that got me thinking: that single number a_ij then uniformly scales every single element within the corresponding Value vector V_j (or the head's d_k slice of V_j) when you do the weighted sum. It’s basically like the attention mechanism looks at Q_i and K_j and decides, "Okay, V_j is like, 70% important overall," and then just multiplies the whole damn thing by 0.7. Every dimension in that V_j chunk gets the same blunt scaling factor.

What If Attention Was... Pickier?

But what if you wanted attention to be... I don't know, more picky? I was thinking, why not give a different weight to each dimension within that Value chunk (V_j), instead of applying the same single scalar weight (a_ij) to all of them? It feels like that should give the model more freedom, right? Like, maybe the relationship between Q_i and K_j tells us that the first few dimensions of V_j are super relevant, but the later ones aren't really needed for this specific query. Standard attention just doesn't let you do that directly; that single scalar weight hits the whole V_j chunk globally.

Crazy Thought: What if num_heads = d_model?

And that led to a thought: What actually happens if you crank the number of heads all the way up to the embedding dimension (num_heads = d_model)? Remember, head_dim = d_model // num_heads. So, yeah, if num_heads = d_model, then head_dim slams down to exactly 1!

What does that even mean?

  1. Each of the d_model heads is doing its attention dance based on just a single scalar number sliced from the projected Q, K, and V tensors.
  2. The attention calculation inside a head h comparing query i and key j? Basically just multiplying two scalars (q_scalar_h_i * k_scalar_h_j). Dead simple.
  3. The "Value vector" for that head? Also just one scalar.
  4. So, each head spits out a single scalar (a weighted sum of scalars).
  5. You concatenate those d_model scalar results from all the heads, and bam, you've reconstructed a d_model vector.

You end up with d_model parallel attention calculations, but they're all working purely at the scalar level comparing single numbers, weighting single numbers. Kind of a wild edge case, right? It seems like it might give that dimension-level control I was wondering about, but in a super weird, atomized way. Definitely not how people usually run MHA (where d_k is usually something like 64), but interesting to noodle on. But, this requires much more compute, which might not be worth it.

Hang On, Do Q, K, and V Need the Same Dimension? (Spoiler: No!)

Okay, speaking of dimensions and assumptions... We usually learn MHA, and see it implemented, where the projected Q, K, and V within a head all share the same dimension, d_k = d_model / num_heads. And yeah, Query (Q) and Key (K) have to have the same dimension (d_k) inside the head you can't do the scaled dot product (Q @ K^T) otherwise. Makes sense.

But here’s the kicker people sometimes miss: the Value (V) dimension doesn't have to match Q and K!

You could absolutely project V to have a different dimension, let's call it d_v, which might be different from d_k. The process would look like this:

  1. Calculate the scalar attention scores a_ij using Q (dim d_k) and K (dim d_k).
  2. Use those scores a_ij to weight the corresponding V vectors (which now have dim d_v). The output of a single head would then have dimension d_v.
  3. Concatenate the outputs from all h heads, resulting in a vector of dimension h * d_v.
  4. That final output projection layer (W_O) then takes this big h * d_v vector and maps it back down to the desired model dimension (d_model).

So, the dimension used for the comparison (d_k for Q and K) can be separated from the dimension of the information being aggregated (d_v for V). This flexibility is often glossed over!

Why This Matters: V is Where the Action Is (Maybe)

And this separation is cool because, let's face it, while Q and K do the important job of figuring out what to focus on, V is where the actual content is. It's the stuff that gets averaged together and passed on.

It probably won't shock you then, that some interesting research pops up when people start messing directly with the Value stream. If V is carrying the payload, maybe tweaking V itself pays off? Folks have found performance bumps by doing things like:

  • Adding value residuals (like, adding the V from previous layers or something similar).
  • Applying activation functions directly to V before weighting.

It seems like focusing some innovation on the Value pathway might be a pretty good bet for squeezing more performance out of these models.

But digging into all the specific ways you can tweak the Value stream? That’s definitely getting into the weeds and is probably a whole other post.
